# testbed

Validate the director against a disposable sample project — offline with fake runners, or by
hand with a real claude/opencode session. Everything under `testbed/run/` is generated by
`setup` and gitignored; committing new validation ideas means editing this folder and
`sample-app`.

```
testbed/
  sample-app/     a tiny real app the director manages (bun test passes)
  projects/       project file for it, with the path token TESTBED/ resolved by setup
  runners/        fake claude/opencode/codex/ao so the eval needs no LLMs
  specs/          one-file runner specs, copied into WD_HOME/runners at setup
  lib.ts          shared paths + setup(); eval.ts, setup.ts
  eval.ts         offline end-to-end: drives the real wd CLI through the whole epic flow
  setup.ts        remakes run/ and prints how to drive it by hand
  run/            (gitignored) sample repo + WD_HOME state + env files
```

## Offline end-to-end (no LLMs)

```
bun testbed/eval.ts
```

Runs `setup`, then real `wd` commands against a throwaway copy of the sample project:
epic + task list grouped by heading (`--json` too), claims, impact, conflict detection/clear,
concerns, task briefs on the shared epic worktree, report → review, soft-done (task: no
verify/PR gate), on-demand private worktree, the merge gate (refuses before a passing
`wd verify`), merge, epic close (all tasks + DONE report + verify + PR), and promotion scan.
## Drive it by hand (real runner)

```
bun testbed/setup.ts
set -a; source testbed/run/.env-manual; set +a
wd status
wd add sample-app "<title>" --kind epic
wd add sample-app "<task>" --epic <id> --heading "<h>"
wd epic spawn <id> --count 2
# then as sessions report: claim/impact/conflict/concern/verify/merge/soft-done/done
```

`.env-manual` only flips `WD_HOME`/`WD_PROJECTS` so a real claude session drives
`testbed/run/sample-app`; your real HOME and PATH (runner) are untouched. The project is
`mode: ask`, so expect confirmation prompts. `wd --help`-style usage is in the repo README;
the design and recorded decisions live in `docs/superpowers/specs/2026-09-25-work-director-parallel-orchestration.md`.

## Notes

- `bun testbed/setup.ts` wipes and remakes `run/` — any state you hand-created is gone.
- The sample project uses `verify: [bun test]` and lists `/lazyspec` in its workflows, so the
  eval exercises a real verify pass and the brief's "lazyspec rides the repo's own files" model.
- `package.json` runs the eval as `bun run testbed`.
